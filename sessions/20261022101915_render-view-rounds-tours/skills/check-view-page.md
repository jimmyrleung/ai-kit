# check-view-page (draft)

Goal: prove the page works as a reader uses it, not only that the build ran.

## Steps

1. Build with the doc path the reader will open (`render_view.py build <spec>/<doc>.md`). For private specs, copy
   the folder's `*.md` (and `.views/exhibits/` if needed) into a scratch folder first, so no test output lands in
   the private tree.
2. Serve the folder in the background: `uv run --no-project python -B -m http.server <port> --bind 127.0.0.1`. The
   Chrome extension refuses `file://` pages.
3. Open `http://127.0.0.1:<port>/.views/view.html` and read console errors.
4. Drive the page with page scripts rather than coordinates, and return a JSON summary:
   - rounds: answer a card, mark a premise for correction (dependent cards flag), filter "Need you", bulk accept,
     comment, then read the live Respond text and the "N to answer" count; reload and confirm answers persisted;
   - tours: toggle Reviewed, the "Not in any step" filter, previous/next links, and the Respond progress lines.
5. Take one screenshot of the changed area; check that `hidden` elements are really hidden (a `display` rule can
   override the attribute).
6. Phone width: the window resize may not change the viewport; load the page in a 390px same-origin iframe and
   compare `scrollWidth` with `clientWidth`.
7. Close the tab and stop the server.

## Notes

- Screenshots can time out once; check the page responds before assuming it hung.
- After a push, without `gh`, read Actions status from
  `https://api.github.com/repos/<owner>/<repo>/actions/runs?branch=main&per_page=3`.
